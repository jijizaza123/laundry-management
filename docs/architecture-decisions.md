# 架构决策记录（ADR）

面试里"你为什么这么设计"比"你做了什么"更难答。这份记录按 **背景 → 备选 → 决定 → 代价 → 什么时候该改** 五段写，
每条都能直接背下来讲。不写"最佳实践"，只写这个项目为什么这么选。

---

## ADR-1 单进程单体 + 分层，而不是微服务

**背景**：课设级洗衣店系统，日单量几十单，一台机器跑。

**备选**：① 拆成用户服务 / 订单服务 / Agent 服务三个进程；② 单进程 FastAPI + 分层目录。

**决定**：②。`routers/` 只做参数解析，`services/` 是唯一业务入口，REST 和 Agent 工具调用同一份 service。

**代价**：无法按服务独立扩容；所有模块共享同一个 SQLite 文件。

**理由**：拆微服务的收益（独立部署、技术栈隔离）在单机几十 QPS 的场景下等于零，而代价是分布式事务、
服务间鉴权、链路追踪全都要补——这些恰好是我没时间做扎实的部分。**"看起来像大厂"不等于"讲得清"**，
单体分层反而能在面试里讲清"一个请求从 HTTP 到落库经过哪几层"。

**什么时候该改**：单机 QPS 打满（本机实测 76 QPS，见 README 压测表）、或需要按团队分工独立发布时。

## ADR-2 预约与洗衣单拆两张表（两层单）

**背景**：上门取件要记"什么时候去谁家取"，洗衣单要记"洗了什么、多少钱、洗到哪一步"。

**备选**：① 塞一张表，加 `appointment_time` / `pickup_time` 两个字段；② 两张表 + `orders.appointment_id` 外键。

**决定**：②。

**代价**：多一次关联查询；客户下单时"顺便预约"要多写一步；取消预约要决定"已生成的洗衣单怎么办"（现在规则是：预约取消不影响已生成的单，因为衣服可能已经取走了）。

**理由**：一张表会让"取件时间"和"取衣时间"在语义上打架，还会出现"预约取消了但单还在""一张预约来了两趟衣服要生成两张单"这类
一对多关系硬塞进一对一表结构的经典错误。拆开之后状态机各自独立：预约是 `pending → confirmed → picked → cancelled`，
订单是 `received → washing → ready → completed / cancelled`，两者用外键关联但互不阻塞。

**什么时候该改**：不需要改。这是正确的建模，不是妥协。

## ADR-3 客户线上单必须"到店复核 + 客户确认"才能结算

**背景**：客户自己在线上填件数，师傅到店点数发现不一致（少报两件、面料从棉说成羊绒）。

**备选**：① 信客户填的，直接按客户填的算；② 师傅改金额，改完立即生效；③ 师傅调价 → 客户确认 → 才能结算。

**决定**：③。`review_status` 四态 `pending / adjusted / confirmed`，`complete_order` 里前置校验，
`pending` 或 `adjusted` 一律 409。

**代价**：多一步交互，客户不点确认单子就卡住（所以补了站内消息 + 导航红点，见 ADR-7）。

**理由**：这是**钱**的问题。②的问题在项目里真实发生过：调价到 ¥105、客户没确认、`washing → ready → complete`
仍然结算成功拿走 ¥105——"客户同意"只是师傅自觉，代码里没有任何约束。①的问题更直接：客户少报件数就是门店亏钱。

**什么时候该改**：接入线上支付时，把"确认金额"和"支付"合成一次签名，`review_status` 可以退化成支付流水的一个字段。

## ADR-4 老客户账号只能门店开通，不开放自助认领

**背景**：店里有 7 个历史客户档案（手机号 + 姓名 + 订单），客户想用手机号注册客户端看自己的单。

**备选**：① 手机号注册即自动关联历史档案（原本的实现）；② 注册后要求门店审核；③ 自助注册只允许全新手机号，老档案必须门店开通。

**决定**：③。`POST /api/customer/register` 遇到已存在档案直接 409；门店用 `POST /api/customers/{id}/bind-account`
开通（后端校验手机号与档案一致 + 密码强度 + 查重）。

**代价**：老客户首次使用必须到店或打电话让店里开通，转化率会掉。

**理由**：①的问题不是"体验"而是**越权**：任何人输入别人手机号就能注册，然后看到对方的姓名、地址、
历史订单和消费金额。没有短信验证的前提下，手机号不是身份凭证，只是一个公开的字符串。
③把"证明你是这个手机号的主人"这件事交给线下门店——这是现实里洗衣店的做法（办卡要本人到场）。

**什么时候该改**：接短信验证码或微信授权后，可以开放自助认领，把校验换成"验证码 + 档案手机号匹配"。

## ADR-5 Agent 动作卡放进程内存（ACTION_STORE），固定单 worker

**背景**：员工 Agent 的写操作是两段式——模型只提议，员工点"确认执行"才落库。提议和确认之间要暂存动作。

**备选**：① 进程内存字典（TTL 600 秒，按 `staff_id` 隔离）；② 落表；③ Redis。

**决定**：①。

**代价**：**只能单进程部署**（`uvicorn --workers 2` 会让确认请求打到没有那个动作的进程，直接失败）；
进程重启后未确认的动作丢失；无法审计"谁提议过什么"。

**理由**：动作卡的生命周期是秒级（员工看到就会点，或者就不点了），不需要跨进程、不需要持久。
用表或 Redis 会引入"清理过期动作"的后台任务和一次额外的网络往返，换来的能力在这个场景下没人用。

**什么时候该改**：要横向扩容（`workers > 1` 或上多容器）时，`staff_tools.py` 里的 `ACTION_STORE`
换成表或 Redis，接口形状（`put / pop / ttl`）保持不变，调用方不用动。这也是 Dockerfile 里写死单 worker 的原因。

## ADR-6 删除订单改成软删，取消订单写红冲

**背景**：原实现 `delete_order` 直接 `DELETE` 订单行 + 明细 + 流水；`cancel_order` 只改状态不记退款。

**备选**：① 保持硬删；② 硬删但先备份流水到日志表；③ 软删（`is_deleted=1`）+ 取消时写负数 `refund` 流水。

**决定**：③。

**代价**：所有查询都要记得加 `is_deleted == 0` 过滤（漏一处就会出现"删了还在列表里"）；
表会越来越大。

**理由**：财务数据不能真删。删掉的单如果流水也没了，月底对账时"钱去哪了"永远说不清；
取消订单如果不记红冲，收入合计会比实际多。①和②都是"数据看起来没了但还是能查"，不如显式软删——
让"对用户隐藏"和"对财务留痕"成为两个独立的开关，而不是一个 `DELETE` 同时决定两件事。

**什么时候该改**：数据量到百万级、需要归档冷数据时，加"归档表 + 定期搬迁"，不要改回硬删。

## ADR-7 站内消息用进程内轮询，而不是 WebSocket

**背景**：调价、可取衣、预约变化需要通知到客户。

**备选**：① WebSocket 推送；② 站内消息表 + 前端轮询未读数；③ 短信/微信推送。

**决定**：②（`notifications` 表 + `GET /api/my/notifications`，导航红点在每次 `meGuard` 后拉一次未读数）。

**代价**：不是实时的（页面不刷新就看不到新消息）；每次进页面多一个请求。

**理由**：①需要长连接管理、断线重连、多进程广播（而本项目固定单进程，见 ADR-5），复杂度对"看一眼消息"这件事过高；
③需要真实短信通道和费用，课设环境不可得。②的价值在于**可审计**：每条消息都在表里，能查"这条调价通知什么时候发给了谁"。

**什么时候该改**：真要做实时（比如师傅调价后客户页面立刻弹提示），在②的表结构上叠 WebSocket 推送即可——消息表仍是唯一真相源。

## ADR-8 测试一律跑临时库副本，不碰 laundry.db

**背景**：本地 `laundry.db` 里有真实演示数据，测试会建单、改状态、扣库存。

**备选**：① 测试直接跑主库（跑完再清理）；② 每个测试套件 `shutil.copy` 一份到 `%TEMP%`，用
`LAUNDRY_DATABASE_URL` 指过去；③ 引 pytest + fixture + 内存 SQLite。

**决定**：②。

**代价**：每个套件多一次文件拷贝（毫秒级）；测试之间不能共享数据，各自准备自己的前置数据。

**理由**：①已经踩过两次——测试跑完主库多了订单、少了库存，演示数据被污染；③需要引入 pytest 依赖并重写
7 个已有的 `check()` 风格脚本，收益只是"更规范"。②是零成本隔离：一次 `copy`，环境变量指过去，进程退出后
临时文件随便扔。

**什么时候该改**：测试数量再涨一倍、需要 fixture 复用和并行执行时，迁到 pytest + `tmp_path`，断言逻辑可以原样搬。
